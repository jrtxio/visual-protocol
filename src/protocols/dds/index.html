DDS 协议学习

数据分发服务 — OMG DDS 标准 — 发布/订阅中间件

DDS 协议基础概念

DDS（Data Distribution Service）是 OMG 组织定义的发布/订阅模式数据分发中间件标准，提供去中心化、低延迟、高可靠的数据通信能力，广泛用于自动驾驶、航空航天、工业控制等实时系统。

核心概念详解

📡 DCPS 模型

数据为中心的发布/订阅模型（Data-Centric Publish-Subscribe）。DDS 的核心抽象层，定义了 Domain、Participant、Publisher、Subscriber、DataWriter、DataReader、Topic 七个核心实体，构成完整的数据分发拓扑。

🌐 Domain（域）

DDS 通信的逻辑隔离边界。同一 Domain 内的参与者可以发现并通信，不同 Domain 之间完全隔离。Domain 由 Domain ID 标识，映射到 UDP 多播端口。典型车载场景：Domain 0 用于控制信号，Domain 10 用于传感器数据。

👤 Participant（参与者）

Domain 中的通信节点，一个进程通常对应一个 Participant。每个 Participant 拥有唯一的 GUID（Global Unique Identifier），包含主机地址、进程 ID 和实体序号。是 Publisher、Subscriber 和 Topic 的容器。

📝 Topic（主题）

数据的类型标识和内容描述。Topic 由名称 + 数据类型定义，是 Publisher 和 Subscriber 之间的匹配纽带。例如 "SensorData" 主题定义了传感器数据的结构和语义，Publisher 向此主题写数据，Subscriber 从此主题读数据。

✍️ DataWriter / DataReader

DataWriter 是应用向 DDS 写入数据的接口，应用调用 write() 方法将数据发布到 Topic；DataReader 是应用从 DDS 读取数据的接口，通过 take() 或 read() 获取数据。两者都受 QoS 策略约束。

⚙️ QoS 策略

服务质量策略（Quality of Service），DDS 提供超过 22 种 QoS 策略来精细控制通信行为：Reliability（可靠/尽力）、Durability（持久性）、History（历史深度）、Deadline（截止时间）、Liveliness（活跃检测）等。QoS 匹配是 Publisher 和 Subscriber 建立关联的前提。

🔍 发现协议

DDS 通过 RTPS 发现协议自动发现网络中的参与者：SPDP（Simple Participant Discovery Protocol）发现对端参与者，SEDP（Simple Endpoint Discovery Protocol）交换端点（DataWriter/DataReader）的 Topic、QoS 等信息。基于 UDP 多播实现，无需中心化注册服务。

🤖 ROS 2 集成

ROS 2 的 rmw（ROS Middleware）层默认使用 DDS 作为底层通信机制。ROS 2 节点对应 DDS Participant，话题对应 Topic，服务通过 Topic + Request/Reply IDL 实现。切换 DDS 实现（Fast DDS、Cyclone DDS、Connext）只需改环境变量，应用代码无需修改。

📄 IDL 接口定义

IDL（Interface Definition Language）是 DDS 定义数据类型的语言，独立于编程语言。用 IDL 定义 struct、enum、union 等数据结构后，DDS 工具链自动生成 C/C++/Java/Python 的类型代码和序列化/反序列化逻辑，确保多语言互操作。

🔄 vs SOME/IP

同属中间件层但模式不同：SOME/IP 采用请求/响应模式（RPC），服务于 AUTOSAR 生态的 ECU 间通信；DDS 采用发布/订阅模式，强调去中心化、QoS 控制和多对多通信，服务于 ROS 2 生态的自动驾驶和机器人场景。两者可共存于同一车载以太网。

协议栈结构

DDS 协议栈从上到下共 5 层，应用数据经 DCPS API 写入后通过 RTPS 线协议在 UDP 上传输。
