MQTT 协议学习

消息队列遥测传输 — 轻量级 IoT 通信协议 — 发布/订阅模型

MQTT 协议基础概念

MQTT（Message Queuing Telemetry Transport）是 OASIS 定义的轻量级发布/订阅消息传输协议，设计目标是低带宽、高延迟网络环境下的可靠消息传递，广泛应用于物联网（IoT）、车联网、工业遥测等场景。

核心概念详解

📡 发布/订阅模型

MQTT 采用解耦的发布/订阅模式。发布者（Publisher）将消息发送到主题（Topic），订阅者（Subscriber）通过订阅主题接收消息。发布者和订阅者互不知道对方的存在，通过 Broker 中转。与 DDS 的去中心化 Pub/Sub 不同，MQTT 需要中心化 Broker。

🖥️ Broker（消息代理）

Broker 是 MQTT 的核心中枢，负责接收所有发布消息并转发给匹配的订阅者。Broker 维护订阅关系、处理 QoS、保留消息和 Will 消息。常见实现：Mosquitto、EMQX、HiveMQ。

🏷️ Topic 主题层级

Topic 使用 / 分隔层级，如 vehicle/001/sensor/temperature。支持通配符：+ 匹配单层级（vehicle/+/temperature），# 匹配多层级（vehicle/001/#）。Topic 在订阅时指定，不是预先注册的。

⚡ QoS 0 — 最多一次

发送方发送消息后不等待确认，消息可能丢失。最低开销、最低延迟。适合高频传感器数据（丢失几条无影响）。

✅ QoS 1 — 至少一次

发送方等待 PUBACK 确认，超时重发。保证消息到达，但可能重复。适合需要可靠但不介意重复的场景（如命令下发后幂等处理）。

🔒 QoS 2 — 恰好一次

四步握手（PUBLISH → PUBREC → PUBREL → PUBCOMP）保证消息恰好到达一次。最高可靠性但最大延迟。适合计费、支付等不可重复的场景。

📌 Retained Message（保留消息）

Broker 保留每个 Topic 最新的一条 Retained 消息。新订阅者订阅时立即收到该保留消息，无需等待下一次发布。适合设备状态等"最新值"场景。

📝 Will Message（遗嘱消息）

客户端连接时可以注册一个 Will Message。当 Broker 检测到客户端异常断开（非 DISCONNECT）时，自动发布其 Will Message。用于通知其他客户端该设备离线。

🔄 Clean Session

Clean Session=1（默认）：断开后 Broker 清除所有订阅和未送达消息；Clean Session=0：Broker 保存会话状态，重连后恢复订阅和推送离线期间的消息。MQTT 5.0 中扩展为 Clean Start + Session Expiry Interval。

📊 与 DDS 对比

MQTT 轻量级、中心化 Broker、简单 QoS（3 级）、适合 IoT/云端通信；DDS 去中心化、丰富 QoS（22+ 策略）、适合实时/车内通信。两者都采用发布/订阅模式但定位不同。

📡 MQTT 报文结构详解

MQTT 报文由固定头（Fixed Header）+ 可变头（Variable Header）+ 负载（Payload）组成，点击卡片查看详情

Fixed Header 结构

每个 MQTT 报文都以固定头开始。第一个字节的高 4 位是报文类型（Packet Type），低 4 位是标志位（Flags）。从第二个字节开始是剩余长度（Remaining Length），使用可变长度编码：每个字节的最高位为延续位，低 7 位为数值，最多 4 字节可编码最大 256MB。
